Why the “Predicted values must be in range [0, 1]” error cannot happen with this file

That error has two causes, both engineered out here and both re-checked against the bytes on disk: (1) the GeoDAWN feature raster's float32 sentinel -3.4028234663852886e+38 leaking into the prediction, and (2) a footprint mask derived from a feature band leaving scored pixels as NaN. This file is written by gems61.submission_writer.write_submission, which refuses to write anything that is not already finite and inside [0, 1], then re-reads the TIFF from disk and aborts unless every one of the 12,279,160 cells passes. In practice this file's values are exactly {0.0, 1.0}.

What the file is, physically

4,583 binary dots on the 100 m competition grid, one per 3 × 3 tile, at the Blakely–Simpson maxima of |grad depth| of the 200 m Parker/Oldenburg inversion of the isostatic residual (band 13), restricted to steps with a measured throw ≥ 80 m that sit in the basin interior (depth > 100 m, the buried domain), ranked by throw, and pruned so that no dot lies within 2 px (200 m) of a mapped trace. This is the lane paragraph's construction, emitted as dots because the metric charges 0.2 per extra positive pixel (ribbons were re-measured this lane and cost ~2× more than they return).
